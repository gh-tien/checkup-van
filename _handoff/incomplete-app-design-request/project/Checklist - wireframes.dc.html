5Draft changes — three ways to make it less confusing

What confuses today: two verbs (Undo vs Restore), three coloured badges, and a mixed list with no plain statement of what publishing will actually do. All three fixes below: plain-English summary at the top, one verb, and a clear primary Publish. 5a groups by action, 5b reads as plain sentences, 5c is a compact before→after diff.

4Templates hub — the builder generalised (Checklist becomes card #1)

Your checklist screen IS a form/template builder. A van intake form, a defect form, a handover form are the same shape (sections → items → response types → draft/publish/version). So the pattern is More → Templates → [card] → the builder you already have. 4a is the hub, 4b the card opened (= the current Checklist), 4c where version history (gap #5) lives per template. Build the hub thin now (one real card → existing builder); add template kinds only when the van form actually lands.

2The conventional pattern — clean read-list + one Draft changes bucket

How form/checklist builders (SafetyCulture, Process Street, Notion, most CMSs) actually do it: the list is a calm read view, editing is a mode you enter per row, and every pending change — added, edited, removed — collects in ONE draft changes place that Publish promotes to a new version. This folds your Holding bay + “not yet live” banner into a single idea and the restore round-trip bug disappears (removed is just a change you can undo). 2a is the list, 2b the tap-to-edit sheet, 2c the draft review.

1Checklist — retire → holding → restore → remove

The bug in the built screen: retire an item → it lands in Holding; Restore it → it goes back; retire it again → it does not return to Holding. Cause: “retire”, “restore” and “delete for good” share one status field, so restore leaves the item in a state the retire button no longer recognises. Below are three ways to model the flow so it round-trips cleanly. Each phone shows one state; the strip under it is the state machine it implies.
